= Try it: failure drills
:description: Watch each safeguard work on the running system, or remove it and watch its test fail.

Each xref:architecture:consistency/index.adoc[failure story] can be tried in up to two ways:

* *Live:* provoke the situation on the running system and watch what it does.
* *Break it:* remove the safeguard on a throwaway branch and run the test that proves it; the red
  output shows exactly what the safeguard prevents.

What the results mean is explained on each story's page.

== Setup, once per terminal

The whole system running (xref:local-run.adoc[local run]), plus Kafka UI
(`docker compose --profile tools up -d`, http://localhost:8090). From the code repository:

[source,bash]
----
source scripts/drills.sh     # loads the helpers below
drill_setup                  # tokens, a product with 10 units in $SKU, bob's profile
----

[cols="1,3"]
|===
|Helper |Does

|`fresh` |New tokens for `$ADMIN` and `$BOB`; they live 15 minutes, so run it again after a `401`.
|`place [card]` |Places one unit of `$SKU` as bob, waits for the saga, prints the order id. The card
token picks the payment outcome: `tok_ok` (default), `tok_decline`, `tok_slow`, `tok_capture_fails`.
|`show <order>` |The order's status and payment status, its shipment's status (or `none`), and the stock.
|`cancel <order>` |Cancels the order as bob; prints the HTTP status.
|`dispatch <order>` |Dispatches the order's shipment as the warehouse; prints the HTTP status.
|`payment <order>` |payment-service's payment row, ledger entries and refunds for the order (from its database).
|`delivered [qty] [card]` |Places an order for `qty` units of `$SKU`, ships and delivers it; prints the order id.
|`ret <order> [qty]` |Asks to return `qty` units of `$SKU` as bob; prints the HTTP status and the return id (or the refusal).
|`receive <return>` |The back office receives the returned parcel; prints the HTTP status and the return's status.
|`returns <order>` |The order's returns and how many units of each SKU they hold.
|`dl` |order-service's dead-letter counter, with its tags.
|`outbox` |order-service's outbox: messages waiting for Kafka, and the age of the oldest.
|`send_event <topic> <key> <type> <data>` |Publishes an event as if a service had sent it.
|`race [delay]` |One round of the cancellation race (drill 1).
|===

The helpers are in {code-tree}/scripts/drills.sh[`scripts/drills.sh`].

To throw away a *Break it* change afterwards:

[source,bash]
----
git switch -c lab/<drill>
# change the code as described, run the test, read the failure
git restore . && git switch - && git branch -D lab/<drill>
----

== 1. A cancellation racing a dispatch

Story: xref:architecture:consistency/cancel-dispatch-race.adoc[A cancellation racing a dispatch].

=== Live

One round: a confirmed order, then the customer's cancellation and the warehouse's dispatch at once.
The optional argument delays the dispatch.

[source,bash]
----
race       # both at once
race 2     # the dispatch two seconds later
----

[cols="1,2,2"]
|===
|Run |Typical result |Why

|`race`
|cancel `202`, dispatch `200`; order `SHIPPED`, shipment `DISPATCHED`; `onHand` one lower, nothing reserved
|The request reaches shipping through the outbox and Kafka (up to a second); the dispatch is a direct
call. The parcel has left before the request arrives, so shipping answers `cancellation-refused`.

|`race 2`
|cancel `202`, dispatch `409`; order and shipment `CANCELLED`; stock available again
|The request arrives first: shipping cancels the shipment, the order becomes `CANCELLED`, catalog
releases the reservation, and the late dispatch is refused.
|===

Either way, order, shipment and stock agree. In Kafka UI, topic `shipping.shipments` filtered by the
order id shows `shipment-dispatched` before `cancellation-refused` after a `race` round.

=== The exact same moment

Both reaching shipping in the same millisecond cannot be hit reliably by hand; the shipment's version
lets only one commit. The test starts both behind one latch, 20 times:

[source,bash]
----
./mvnw verify -pl shipping-service -Dit.test=CancellationRaceIT
----

== 2. A delivery without a dispatch

Story: xref:architecture:consistency/delivery-without-dispatch.adoc[A delivery without a dispatch].

=== Live

A confirmed order that was never dispatched, then a `shipment-delivered` for it, as if the dispatch
event had been lost on the way:

[source,bash]
----
fresh
ORDER=$(place); show $ORDER; dl
send_event shipping.shipments $ORDER shipping.shipment-delivered "{\"shipmentId\":\"$(uuid)\",\"orderId\":\"$ORDER\"}"
sleep 5; show $ORDER; dl
----

[cols="1,2,2"]
|===
| |Before the event |After

|order |`CONFIRMED` |`CONFIRMED`, unchanged
|shipment |`CREATED` |`CREATED`: the parcel never left
|stock |one unit reserved |still reserved, not committed
|dead letters |no counter yet |`1`, `IllegalOrderTransitionException` on `shipping.shipments`
|===

order-service refuses to deliver an order that was never shipped: the event is retried three times,
then moved to `shipping.shipments-dlt`, where Kafka UI shows it with its `kafka_dlt-exception-*`
headers. All shipping events of an order share one topic and key, so they arrive in order: a
delivery without its dispatch means the dispatch was dead-lettered itself, not that it is late.
Both wait side by side in the dead-letter topic, to be replayed dispatch first
(xref:operations:dead-letters.adoc[runbook]).

=== Break it

* *Change:* in `Order.deliver` (order-service), let `CONFIRMED` through like `SHIPPED`.
* *Run:* `./mvnw verify -pl order-service -Dit.test=SagaReactionsIT` and `./mvnw test -pl order-service`
* *Expect:* an order becomes `DELIVERED` although its stock was never committed.

== 3. Orders that stop moving

Story: xref:architecture:consistency/stuck-orders.adoc[Orders that stop moving].

=== Live

Run order-service with expiry in minutes instead of 30 minutes and 3 days (stop the usual instance
first):

[source,bash]
----
./mvnw -q -pl order-service spring-boot:run -Dspring-boot.run.arguments="\
--ecommerce.orders.expiry.placed-after=1m --ecommerce.orders.expiry.confirmed-after=2m \
--ecommerce.orders.expiry.scan-interval=10s"
----

*Part A, confirmed too long.* Every `CONFIRMED` order older than two minutes is asked to cancel;
shipping stops the parcels that have not left, and catalog releases their stock. After a scan,
`reserved` for the drill SKU drops to 0 and bob's older orders show "Not dispatched in time":

[source,bash]
----
curl -s "$GW/orders?customerId=b0b00000-0000-4000-8000-000000000002" -H "Authorization: Bearer $ADMIN" \
  | jq -r '.[:8][] | "\(.status)\t\(.cancellationReason // "")"'
----

*Part B, placed too long.* With Kafka down, a new order cannot get its reservation:

[source,bash]
----
reason() { curl -s $GW/orders/$1 -H "Authorization: Bearer $BOB" | jq -c '{status, cancellationReason}'; }
docker compose stop kafka
ORDER=$(place); reason $ORDER
sleep 80; reason $ORDER
docker compose start kafka
sleep 25; show $ORDER
----

The order is `PLACED`, then `CANCELLED` with "Not confirmed in time" while Kafka is still down:
expiry needs only order-service's database, and its `order-cancelled` waits in the outbox. Once
Kafka is back, catalog receives `order-placed` and `order-cancelled` in that order (one topic, one
key), reserves and releases, and the stock ends where it started.

=== Break it

* *Change:* in `OrderJpaRepository.lockIfFree`, replace `FOR UPDATE SKIP LOCKED` with `FOR UPDATE`.
* *Run:* `./mvnw verify -pl order-service -Dit.test=OrderExpiryIT`
* *Expect:* still green. Why? The second scanner now waits instead of skipping, then re-checks the
  status under the lock and finds the order already handled. `SKIP LOCKED` is about throughput; the
  re-check is what makes it correct. Now remove the re-check too and run again.

== 4. Failures nobody sees

Story: xref:architecture:consistency/silent-failures.adoc[Failures nobody sees].

=== Live, part A: a message nobody can process

[source,bash]
----
dl
echo "not json" | docker compose exec -T kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic shipping.shipments
sleep 2; dl
----

The counter rises by one, tagged `exception=MalformedEventException`. It is faster than drill 2:
an unreadable record skips the retries, because reading it again gives the same result. The
counter's value is the sum over its tags; one tag alone:
`.../messaging.dead.letters?tag=exception:MalformedEventException`.

`shipping.shipments` has two consumers, order-service and catalog-service, each in its own group:
catalog's counter (port 8081) rises too, and `shipping.shipments-dlt` holds two copies. One bad
message, two dead letters.

=== Live, part B: messages that cannot leave

[source,bash]
----
outbox
docker compose stop kafka
ORDER=$(place); show $ORDER; outbox
sleep 15; outbox
docker compose start kafka
sleep 20; outbox; show $ORDER
----

[cols="1,2"]
|===
|Moment |What you see

|Kafka stopped, order placed
|The order is accepted (`PLACED`); bob gets no error. Order and event were stored in one transaction.

|Right after, and 15 seconds later
|`outbox.pending` 1; `outbox.oldest.pending.age` 2 s, then 17 s and growing.

|Kafka started, 20 seconds later
|Pending 0, age 0: the relay published by itself. The order is `CONFIRMED`, its shipment `CREATED`,
one more unit reserved: the saga continued where it stopped.
|===

Nothing is lost and nothing has to be redone, but nothing in front of a user shows that events are
stuck either. Only the age does, which is why the alert is "oldest pending over a minute"
(xref:operations:metrics.adoc[metrics and alerts]).

== 5. A replayed order-placed

Story: xref:architecture:consistency/replayed-order-placed.adoc[A replayed order-placed].

=== Live

Reserve, cancel (the reservation is released), then deliver the same `order-placed` again with a new
event id:

[source,bash]
----
fresh
ORDER=$(place); show $ORDER
curl -s -o /dev/null -w 'cancel -> %{http_code}\n' -X POST $GW/orders/$ORDER/cancel \
  -H "Authorization: Bearer $BOB" -H "$J" -d '{"reason":"changed my mind"}'
sleep 4; show $ORDER
send_event order.lifecycle $ORDER order.order-placed \
  "{\"orderId\":\"$ORDER\",\"customerId\":\"b0b00000-0000-4000-8000-000000000002\",\"lines\":[{\"sku\":\"$SKU\",\"quantity\":1,\"unitPrice\":5.00}],\"totalAmount\":5.00,\"currency\":\"EUR\",\"shippingAddress\":\"Kadıköy 1, İstanbul\"}"
sleep 3; show $ORDER
# catalog's answers for this order
docker compose exec -T kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic catalog.reservations --from-beginning --property print.key=true --timeout-ms 5000 2>/dev/null \
  | grep $ORDER | cut -f2- | jq -c '{type: .eventType, reason: .data.reason}'
----

The reserved count drops by one at the cancellation and does not rise again at the replay; the order
stays `CANCELLED`. Catalog's answers are `stock-reserved`, then `stock-reservation-failed`: "The
reservation for order … was released; an order reserves stock once, a new order needs a new id".

=== Break it

* *Change:* in `ReservationService.attemptReservation` (catalog), delete the `if (… RELEASED)` block.
* *Run:* `./mvnw verify -pl catalog-service -Dit.test='SagaParticipationIT#aReplayedOrderPlaced*'`
* *Expect:* the replies are `stock-reserved` twice instead of `stock-reserved` then
  `stock-reservation-failed`: catalog claims stock it does not hold.

== 6. A replayed order-confirmed

Story: xref:architecture:consistency/replayed-order-confirmed.adoc[A replayed order-confirmed].

=== Live

An order catalog cannot reserve is cancelled before shipping ever hears of it. Then shipping gets
the cancellation request (it has no shipment) and, later, the lost confirmation:

[source,bash]
----
fresh
ORDER=$(curl -s -X POST $GW/orders -H "Authorization: Bearer $BOB" -H "$J" -H "Idempotency-Key: $(uuid)" \
  -d "{\"cardToken\":\"tok_ok\",\"lines\":[{\"sku\":\"$SKU\",\"quantity\":100}]}" | jq -r .id)
sleep 2; show $ORDER
send_event order.lifecycle $ORDER order.cancellation-requested "{\"orderId\":\"$ORDER\",\"reason\":\"drill\"}"
sleep 3
docker compose exec -T -e PGPASSWORD=shipping_service postgres psql -h localhost -U shipping_service -d shipping_db \
  -c "select order_id, cancelled_at from cancelled_orders where order_id = '$ORDER'"
send_event order.lifecycle $ORDER order.order-confirmed \
  "{\"orderId\":\"$ORDER\",\"customerId\":\"b0b00000-0000-4000-8000-000000000002\",\"lines\":[{\"sku\":\"$SKU\",\"quantity\":100}],\"shippingAddress\":\"Kadıköy 1, İstanbul\"}"
sleep 3; show $ORDER
----

The order is `CANCELLED` with no shipment; the cancellation request leaves one row in
`cancelled_orders`; after the late confirmation the shipment is still `none`, and shipping-service
logs a warning that the order was confirmed after its cancellation.

=== Break it

* *Change:* in `ShippingService.orderConfirmed`, delete the `cancelledOrders.contains(orderId)` check.
* *Run:* `./mvnw verify -pl shipping-service -Dit.test='ShippingSagaIT#aConfirmationReplayed*'`
* *Expect:* a shipment exists for an order whose cancellation shipping had accepted.

== 7. An inbox that forgets too early

Story: xref:architecture:consistency/inbox-forgets.adoc[An inbox that forgets too early].

=== Live

Start a second order-service (on a random port) with an inbox retention no longer than the topic
retention:

[source,bash]
----
./mvnw -q -pl order-service spring-boot:run \
  -Dspring-boot.run.arguments="--ecommerce.messaging.inbox.retention=7d --server.port=0"
----

It stops with `APPLICATION FAILED TO START`: "ecommerce.messaging.inbox.retention (PT168H) must be
longer than ecommerce.messaging.topics.retention (PT168H): events Kafka can still redeliver would be
processed again". The database pool had opened, but the port never did and no listener started: not
a single event was consumed with the dangerous setting.

== 8. A payment provider that does not answer

Story: xref:architecture:consistency/provider-no-answer.adoc[A payment provider that does not answer].

=== Live

`tok_slow` makes the simulated provider place the hold but lose its first answer:

[source,bash]
----
fresh
ORDER=$(place tok_slow); show $ORDER; payment $ORDER
sleep 45; show $ORDER; payment $ORDER
----

Watch payment-service's console (or log) meanwhile.

[cols="1,2"]
|===
|Moment |What you see

|Right after placing
|Order `PLACED, payment AUTHORIZING`, shipment `none`, one unit reserved; payment-service's row
`AUTHORIZING`, `held` false, no ledger entries. payment-service logs
`No answer to AUTHORIZE of payment …; asking again later`.

|About 30–45 s later
|Order `CONFIRMED`, payment `AUTHORIZED`, shipment `CREATED`. payment-service logs `Asked the provider
again about 1 payment(s)`: the resolver asked with the same key and got the hold that was placed.
|===

The order was never declined and never charged twice; it only waited. In the first snapshot the
system says "I don't know" although the simulated provider had in fact placed the hold: only its
answer was lost. That is the honest answer; "declined" would have been wrong.

=== Break it

* *Change:* in `Payment.idempotencyKey` (payment-service), return `UUID.randomUUID() + ":" + …`
  instead of `id + ":" + …`: every attempt becomes a new request to the provider.
* *Run:* `./mvnw test -pl payment-service -Dtest='PaymentServiceTest,PaymentTest'`
* *Expect:* `noAnswerIsNotADecline…` fails: the two attempts used different keys, and to a real
  provider that is two holds on the card.

== 9. A cancellation racing an authorization

Story: xref:architecture:consistency/cancel-during-authorization.adoc[A cancellation racing an authorization].

=== Live

Cancel while the authorization has no answer yet:

[source,bash]
----
fresh
ORDER=$(place tok_slow); cancel $ORDER
sleep 3; show $ORDER; payment $ORDER
docker compose exec -T kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic payment.events --from-beginning --property print.key=true --timeout-ms 5000 2>/dev/null \
  | grep $ORDER | cut -f2- | jq -c '{type: .eventType}'
----

In a run, three seconds after placing:

[source]
----
cancel   -> 200
order    = CANCELLED, payment VOIDED
shipment = none
 status | void_requested | held
 VOIDED | t              | t
(ledger: 0 rows)
----

The order was still `PLACED`, so the cancellation was immediate, the stock released, and
`void-payment` sent. `void_requested = t` is the point of the story: the cancellation arrived while
the authorization had no answer, and payment-service remembered it. `held = t` shows why that
matters: the provider had placed a hold, which would otherwise have stayed on the card of a cancelled
order. It took seconds, not 30: the void request made payment-service ask the provider again at once,
with the same key; the approval came back and was released straight away. On `payment.events` the
order has exactly one event, `payment-voided`: never `payment-authorized`.

=== Break it

* *Change:* in `Payment.authorized`, always move to `AUTHORIZED`, ignoring `voidRequested`.
* *Run:* `./mvnw test -pl payment-service -Dtest='PaymentServiceTest,PaymentTest'`
* *Expect:* `aCancellationDuringAnUnansweredAuthorization…` fails: the payment ends `AUTHORIZED` and
  `payment-authorized` is announced for a cancelled order, whose hold nobody will ever release.

== 10. A capture repeated by a retry

Story: xref:architecture:consistency/repeated-capture.adoc[A capture repeated by a retry].

=== Live

Ship an order, then send its capture command again as if it had been replayed (a new event id, so
the inbox does not recognise it):

[source,bash]
----
fresh
ORDER=$(place); dispatch $ORDER
sleep 3; show $ORDER; payment $ORDER
send_event payment.commands $ORDER payment.capture-payment "{\"orderId\":\"$ORDER\"}"
sleep 3; payment $ORDER
----

In a run:

[source]
----
dispatch -> 200
order    = SHIPPED, payment CAPTURED
  status  | void_requested | held
 CAPTURED | f              | t
  kind   |       account       | amount | currency
 CAPTURE | PROVIDER_RECEIVABLE |   5.00 | EUR
 CAPTURE | SALES               |  -5.00 | EUR
----

After the replayed command, `payment` prints exactly the same. The command had a new event id, so the
inbox did not recognise it; the payment's state machine did: a `CAPTURED` payment ignores a capture
request, so the provider was not called and nothing was booked.

And the ledger defends itself, whatever code writes to it:

[source,bash]
----
docker compose exec -T -e PGPASSWORD=payment_service postgres psql -h localhost -U payment_service -d payment_db \
  -c "update ledger_entries set amount = 0.01"
----

`ERROR: The ledger is append-only: UPDATE on ledger_entries is not allowed`. The refusal comes from
a database trigger, not from Java: a manual "fix" in SQL or a buggy future service cannot rewrite
the books either.

=== Break it

* *Change:* in `LedgerTransaction.capture`, use `UUID.randomUUID().toString()` as the reference
  instead of the capture's idempotency key.
* *Run:* `./mvnw verify -pl payment-service -Dit.test='PaymentPersistenceIT#bookingACaptureTwice*'`
* *Expect:* the second booking is accepted, and the balances are twice the captured amount: revenue
  the shop never received.

== 11. Two return requests at the same moment

Story: xref:architecture:consistency/concurrent-returns.adoc[Two return requests at the same moment].

=== Live

Two units delivered, four requests for one unit each, at once:

[source,bash]
----
fresh
ORDER=$(delivered 2); show $ORDER
for i in 1 2 3 4; do ret $ORDER 1 & done; wait
returns $ORDER
----

Two requests get `201` with a return id, two get `422`: "Not that many units of … can still be
returned: 2 ordered, some already returned". `returns` shows two returns `REQUESTED` and
`returnedUnits` at 2. Which two win depends on timing; that exactly two win does not.

=== Break it

* *Change:* in `JdbcReturnedUnits.take` (order-service), delete the `WHERE` line of the statement.
* *Run:* `./mvnw verify -pl order-service -Dit.test='ReturnApiIT#concurrentRequests*'`
* *Expect:* still only two returns, but eight `500` instead of `422`: the check constraint
  `returned_units_within_order` is the last line, and it holds. The conditional statement is what
  turns the limit into a clear answer. Delete the constraint from `V8` as well (on the lab branch,
  with a fresh database) and ten returns are accepted for two keyboards.

== 12. A return received twice

Story: xref:architecture:consistency/return-received-twice.adoc[A return received twice].

=== Live

Receive one return twice at once, then announce it to catalog again with a new event id:

[source,bash]
----
fresh
ORDER=$(delivered 1); R=$(ret $ORDER 1 | awk '{print $4}'); show $ORDER
receive $R & receive $R & wait
sleep 3; show $ORDER; returns $ORDER; payment $ORDER
send_event order.lifecycle $ORDER order.return-received \
  "{\"returnId\":\"$R\",\"orderId\":\"$ORDER\",\"lines\":[{\"sku\":\"$SKU\",\"quantity\":1}]}"
sleep 3; show $ORDER
----

The two receives answer `200 RECEIVED` and `200 RECEIVED` (the second came after the first had
committed) or one of them `409` (both at the same moment: the version decided). Either way: the stock's
`onHand` rises by one, the return is `REFUNDED` with 5.00, and payment-service has one refund, one
`REFUND` ledger transaction and `refunded_amount` 5.00. After the replayed event, `onHand` does not move.

=== Break it

* *Change:* in `ReturnedStockService.receiptId` (catalog), return `UUID.randomUUID()`.
* *Run:* `./mvnw verify -pl catalog-service -Dit.test='SagaParticipationIT#aReceivedReturn*'`
* *Expect:* `onHand` 14 instead of 12: the replayed announcement restocked the same units again.
  The inbox still stopped the plain redelivery; only the receipt stops a replay with a new id.

== 13. Refunds beyond the capture

Story: xref:architecture:consistency/refunds-beyond-capture.adoc[Refunds beyond the capture].

=== Live

An order paid 5.00, then two refund commands of 3.00 each, as if for two different returns:

[source,bash]
----
fresh
ORDER=$(delivered 1)
for i in 1 2; do
  send_event payment.commands $ORDER payment.refund-payment \
    "{\"orderId\":\"$ORDER\",\"returnId\":\"$(uuid)\",\"amount\":3.00,\"currency\":\"EUR\"}"
done
sleep 3; payment $ORDER
docker compose exec -T -e PGPASSWORD=payment_service postgres psql -h localhost -U payment_service -d payment_db \
  -c "update payments set refunded_amount = amount + 1 where order_id = '$ORDER'"
----

`refunded_amount` 3.00; one refund `REFUNDED` 3.00 and one `FAILED` with "A refund of 3.00 EUR would
exceed the captured 5.00 EUR (3.00 already refunded)"; the ledger shows the capture and one `REFUND`
transaction (`SALES 3.00`, `PROVIDER_RECEIVABLE -3.00`). The refused refund never reached the
provider. The manual update fails on the check constraint `payments_refunds_within_amount`.

order-service knows no returns with these ids, so it dead-letters both answers: `dl` rises by two.
That is the right reaction to answers nobody asked for.

=== Break it

* *Change:* in `JdbcPayments.reserveRefund`, delete `AND refunded_amount + :amount <= amount`.
* *Run:* `./mvnw verify -pl payment-service -Dit.test='PaymentCommandsIT#refunds*'`
* *Expect:* no `payment-refund-failed` for the refund over the limit. The check constraint still
  stops the money, but as an error: the command ends in a dead-letter topic, and order-service is
  never told why its refund did not happen.
