= Sprints and roadmap
:description: What each sprint delivered and what comes next.

The project is built sprint by sprint. A sprint is done when the build is green locally and in CI,
its main claim is proven by an integration test against real PostgreSQL and Kafka, significant
decisions are recorded as ADRs, *these docs are updated*, and the sprint is tagged (`sNN`).

[cols="1,2,4,1"]
|===
|Sprint |Goal |Outcome |Status

|s00 |Foundation |Maven build, local infrastructure, Testcontainers, CI |done
|s01 |Catalog and inventory |Server-side prices; concurrency-safe reserve, commit and release |done
|s02 |Messaging |Transactional outbox with ordered relay, inbox, dead-letter topics |done
|s03 |Customers and orders |Catalog-priced, idempotent order placement; forward-only order status |done
|s04 |Shipping and the saga |Reserve, confirm, ship, deliver, cancel with compensation; end-to-end tests |done
|s05 |Security |Keycloak; resource servers with enforced deny-by-default; service tokens; routing-only gateway |done
|s06 |Saga hardening |Cancellation decided by shipping; delivery only after dispatch; order expiry; outbox and dead-letter metrics; replay guards; inbox retention |done
|s07 |Documentation |This site: role-based guides, domain model, failure stories with live drills, runbooks |done
|s08 |Payments |payment-service commanded by order-service (ADR-0009): authorize before confirming, capture at dispatch, void on cancellation; idempotency keys per provider call; unknown outcomes resolved, never declined; a double-entry ledger the database keeps balanced; three new failure stories |done
|s09 |Returns |Returns in order-service (ADR-0010): within 14 days of delivery, never more than was bought (a database-enforced counter per order line); refund when the goods arrive back, never more than was captured; restock idempotent by return; three new failure stories |done
|s10 |Observability |One trace per order through HTTP, Kafka and the outbox (OpenTelemetry, Jaeger); Prometheus scraping with its own Keycloak client; Grafana dashboard and four alert rules as code; the drill's trace exposed a relay attempt blocking a minute, now capped at the send timeout; one new failure story |done
|s11 |Packaging |Images built by Jib and pushed to GHCR from CI; the whole system with one command (`docker compose --profile app up`); one token issuer inside and outside containers |next
|s12 |Kubernetes and GitOps |A k3d cluster synced by Flux: infrastructure as Helm releases (Strimzi, CloudNativePG, Keycloak, Prometheus stack, Jaeger), services as Kustomize; Kafka users and ACLs; image automation; alerts delivered |planned
|s13+ |Optional |Marketplace (sellers, orders split per seller, split payments and payouts); promotions; back-in-stock notifications |optional

A web console (customer shop and back-office saga view) is built in parallel in

xref:developer:ui-integration.adoc[API and login for the UI]).

== Next: s11 Packaging, then s12 Kubernetes and GitOps

Today the services run from an IDE and the infrastructure from compose. s11 makes each service an
image (Jib, no Dockerfile), publishes the images to GitHub Container Registry from CI, and starts the
whole system with one command (xref:architecture:adr/0012-packaging.adoc[ADR-0012]).

s12 takes the same images to Kubernetes: a k3d cluster that Flux keeps in sync with the repository,
third-party components as Helm releases, our services as Kustomize, Kafka with a user and ACLs per
service, new images rolled out by Flux's image automation, and Alertmanager so the four alert rules
reach a person instead of a web page.
