= FF E-Commerce
:description: An order-to-delivery flow across independent services, built to stay consistent when messages arrive late, twice, or not at all.
:page-role: home

An order-to-delivery flow built as independent services: catalog and inventory, customers, orders,
payments and shipping, each with its own database, talking through Kafka. The focus is on the hard parts of
distributed systems rather than on feature count.

== The question

When stock lives in one database, orders in another and parcels in a third, *what keeps them from
disagreeing?* There is no transaction across them. A message can be delivered twice, late, or end in
a dead-letter topic; a customer can cancel at the very moment the warehouse ships.

Think of three shops on one street, each with its own ledger, passing notes to each other. The notes
sometimes arrive twice, sometimes late, sometimes get lost in a drawer. The system works if every
shop keeps a list of notes it has already handled, never acts on a note that contradicts what it
already knows, and someone checks the drawer.

The answer here is a saga on top of a transactional outbox and an idempotent inbox, with one service
owning each decision that cannot be undone. Catalog and shipping are choreographed; payment, where a
mistake costs money directly, is commanded by order-service.

== Engineering scope

[cols="1,3"]
|===
|Area |What is built

|Consistency
|Concurrency-safe stock reservations; transactional outbox with ordered relay; idempotent inbox;
choreographed saga with compensation; cancellation decided by the owner of the point of no return;
order expiry; payments with idempotent provider calls, unknown outcomes resolved rather than guessed,
and a double-entry ledger the database keeps balanced.

|Security
|Keycloak; every service an OAuth2 resource server with audience checks and enforced
deny-by-default; identity and ownership from the token; service-to-service client credentials.

|Operability
|Dead-letter topics; outbox lag and dead-letter metrics; retention rules that keep idempotency intact.

|Proof
|Integration tests against real PostgreSQL and Kafka (Testcontainers) and end-to-end tests of the
packaged services, including races repeated many times.
|===
