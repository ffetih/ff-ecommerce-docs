= The order saga
:description: How order, catalog, payment and shipping move one order from placement to delivery without a shared transaction.

An order touches four services with their own databases. Instead of one transaction, each service
does its part in a local transaction and announces it with an event. Catalog and shipping react to
order-service's events (choreography, xref:adr/0007-order-saga.adoc[ADR-0007]); payment-service
receives commands from order-service and answers with events
(xref:adr/0009-payments-driven-by-order-service.adoc[ADR-0009]).

  CONFIRMED -> SHIPPED [label="shipment-dispatched"];
  SHIPPED -> DELIVERED [label="shipment-delivered"];
  CONFIRMED -> CANCELLATION_REQUESTED [label="customer cancels\nnot dispatched in 3 days"];
  CANCELLATION_REQUESTED -> CANCELLED [label="shipment-cancelled"];
  CANCELLATION_REQUESTED -> SHIPPED [label="shipment-dispatched\n(dispatch came first)"];

----

The order only moves forward. A step it has already passed is ignored, so a late or repeated event
changes nothing. An order is confirmed only when both its stock and its money are held.

== Payment states, as the order sees them

Next to its status, the order records what it has asked of payment-service. The states ending in
-ING mean a command is on its way; order-service sends the command when the order enters that state,
in the same transaction (outbox).

  AUTHORIZING -> AUTHORIZED [label="payment-authorized\n(order CONFIRMED)"];
  AUTHORIZING -> DECLINED [label="payment-declined\n(order CANCELLED)"];

----

`»` marks the command order-service sends. Orders placed before payments existed stay
`NOT_REQUESTED` and ship without a payment.

== Who reacts to what

[plantuml,saga-sequence,svg]
----
@startuml
skinparam shadowing false
skinparam defaultFontName sans-serif
participant "order-service" as O
queue "order.lifecycle" as OL
participant "catalog-service" as C
queue "catalog.reservations" as CR
participant "shipping-service" as S
queue "shipping.shipments" as SS
queue "payment.commands" as PC
participant "payment-service" as P
queue "payment.events" as PE

O -> OL : order-placed
OL -> C : reserve stock
C -> CR : stock-reserved
CR -> O : payment AUTHORIZING
O -> PC : authorize-payment
PC -> P : hold the amount
P -> PE : payment-authorized
PE -> O : CONFIRMED
O -> OL : order-confirmed
OL -> S : create shipment
== warehouse hands the parcel over ==
S -> SS : shipment-dispatched
SS -> C : commit stock
SS -> O : SHIPPED
O -> PC : capture-payment
PC -> P : take the money, book the ledger
P -> PE : payment-captured
PE -> O : CAPTURED
S -> SS : shipment-delivered
SS -> O : DELIVERED
@enduml
----

All topics are keyed by order id, so the events of one order arrive in order within each topic.

== Cancelling

[cols="1,3"]
|===
|Order is |What happens

|PLACED
|order-service cancels on its own (`200`) and announces `order-cancelled`; catalog releases whatever it
reserved. No shipment exists yet. If the authorization was already asked for, order-service sends
`void-payment`; payment-service remembers it until the provider answers
(xref:consistency/cancel-during-authorization.adoc[story]).

|CONFIRMED
|order-service *asks* (`202`, CANCELLATION_REQUESTED) and announces `cancellation-requested`.
Shipping decides, because only shipping knows whether the parcel has left: before dispatch it cancels
the shipment and answers `shipment-cancelled`, and only then does the order become CANCELLED, the
stock released and the hold on the card voided; after dispatch it answers `cancellation-refused`, the
order stays SHIPPED and the money is captured.

|SHIPPED or later
|`409`. Afterwards it can only become a return, refunded through payments (s09).
|===

== Returns

A delivered order can be returned within 14 days, wholly or in part
(xref:adr/0010-returns-in-order-service.adoc[ADR-0010]). Returns are their own aggregate in
order-service; the refund follows the goods, not the request.

[plantuml,returns-sequence,svg]
----
@startuml
skinparam shadowing false
skinparam defaultFontName sans-serif
actor Customer
actor "Back office" as BO
participant "order-service" as O
queue "order.lifecycle" as OL
participant "catalog-service" as C
queue "payment.commands" as PC
participant "payment-service" as P
queue "payment.events" as PE

Customer -> O : request return (lines, reason)
note right of O : counter per order line:\nnever more than was bought
BO -> O : parcel received
O -> OL : return-received
OL -> C : units back on hand
O -> PC : refund-payment
PC -> P : refund within the capture,\nledger: reversal
P -> PE : payment-refunded
PE -> O : return REFUNDED
@enduml
----

A return the back office rejects counts its units back. A refund the provider refuses leaves the
return `REFUND_FAILED` for operations; the units are back in stock regardless.

The full list of situations and their compensation is in
xref:adr/0007-order-saga.adoc[ADR-0007]; the reasoning behind each rule is in the
xref:consistency/index.adoc[failure stories].
