= A delivery without a dispatch
:description: `shipment-delivered` reaches order-service for an order that never became SHIPPED.

== The scenario

A `shipment-delivered` event reaches order-service for an order that is still `CONFIRMED`. Its predecessor, `shipment-dispatched`, was never applied. That dispatch can be missing at all only because it was dead-lettered itself: every shipping event of one order shares one topic and one key, so Kafka delivers them in order per key, and a later event cannot overtake an earlier one.

== What would go wrong

Accepting the delivery would leave three records in three different truths. The order would say `DELIVERED`, as if the customer had the goods. The shipment would still be `CREATED`, the parcel never having left the warehouse. The stock would stay reserved and never be committed, so the unit would sit blocked. Nobody would look again, because `DELIVERED` is a final state.

== The fix

Order-service accepts a delivery only from `SHIPPED`. On a `CONFIRMED` order it throws, rolls the change back, and the event goes to the dead-letter topic next to the dispatch it depends on. Waiting for the dispatch would not help: the missing event is missing, not late. Whoever fixes the cause replays the two records in order, dispatch first, and the order moves `SHIPPED` then `DELIVERED`.

== How it is proven

* `SagaReactionsIT` (order-service)

Sending a forged `shipment-delivered` for a confirmed order left the order `CONFIRMED`, the shipment `CREATED`, and the stock still reserved, and produced one dead letter: `IllegalOrderTransitionException` on `shipping.shipments`.
