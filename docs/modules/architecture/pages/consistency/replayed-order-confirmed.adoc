= A replayed order-confirmed
:description: An order's confirmation was dead-lettered, shipping accepted its cancellation without a shipment, and later someone replays the dead letter.

== The scenario

An order's `order-confirmed` never reached shipping: it ended in a dead-letter topic. The order is
then cancelled. Shipping has no shipment for it, so it accepts the cancellation at once, the order
becomes `CANCELLED`, and catalog releases the stock. Days later someone fixes the cause and replays
the dead letter: the confirmation arrives after all.

== What would go wrong

Shipping's "yes, cancelled" left no trace in its own database: its only state is its shipments, and
there was nothing to cancel. So the late confirmation looked like any normal confirmed order without
a shipment yet, and shipping created one. The warehouse would pack and dispatch a parcel for a
cancelled order whose stock was already released, and catalog would refuse to commit that stock.

== The fix

A decision must leave a trace in the service that made it. When shipping accepts a cancellation
without a shipment, it records the order in `cancelled_orders`, in the same transaction as its
answer. A confirmation for a recorded order creates nothing and logs a warning instead. Ordering per
key still holds: the replay only matters because it arrives after the cancellation.

== How it is proven

* `ShippingSagaIT`

In a manual run, an order that catalog could not reserve was cancelled before shipping heard of it.
A cancellation request then left a row in `cancelled_orders`, and a late `order-confirmed` for the
same order created no shipment: shipping still showed none.
