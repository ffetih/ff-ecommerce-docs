= A replayed order-placed
:description: `order-placed` arrives again after the order was cancelled and its reservation released, and the inbox no longer recognises it.

== The scenario

An order was reserved, then cancelled, and catalog released its stock. Later the same `order-placed`
arrives again with an id the inbox does not recognise, for example replayed from a dead-letter topic
or after the inbox has forgotten it. Catalog finds a reservation for this order with exactly the same
lines.

== What would go wrong

Catalog treated a matching reservation as a retry and gave the same answer again: `stock-reserved`.
But that reservation was released; no stock was held. The saga survived it, because a cancelled
order ignores the answer and releases again, which changes nothing. But catalog stated something
false, and once payments follow a reservation, a false "reserved" can cost real money. Idempotency
means the same effect, not the same words when they are no longer true.

== The fix

A reservation lives once: `RESERVED`, then `COMMITTED` or `RELEASED`, never again. Catalog refuses
to reserve for an order whose reservation was released and answers `stock-reservation-failed`,
saying why; over HTTP the same request gets `409`. The rule spans the stored reservation and the new
request, so it lives in the application service, not in one aggregate.

== How it is proven

* `SagaParticipationIT`
* `ReservationLifecycleIT`

In a manual run, an order was reserved (3 units reserved for the SKU), cancelled (2), and its
`order-placed` replayed with a new event id: the count stayed at 2, the order stayed `CANCELLED`,
and catalog's answers for the order were `stock-reserved`, then `stock-reservation-failed` with
"the reservation for order … was released; an order reserves stock once, a new order needs a new id".
