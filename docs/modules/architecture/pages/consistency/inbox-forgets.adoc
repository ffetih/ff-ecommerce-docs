= An inbox that forgets too early
:description: A consumer group's offsets are lost, and Kafka delivers everything still in the topic again.

== The scenario

A consumer group loses its committed offsets: they expire while a service is down longer than Kafka
keeps them, or an operator resets them. The group then starts again from the oldest record still in
the topic, and every event of the last days is delivered a second time. The inbox recognises a
redelivered event only as long as it still remembers the event's id.

== What would go wrong

If the inbox had already forgotten those ids, every redelivered event would look new. Catalog would
reserve stock again for old orders, shipping would answer old requests again, and orders would move
in ways nobody asked for. The cause would be a retention setting changed weeks earlier, and nobody
would connect the two.

== The fix

Every topic is created with an explicit retention (7 days), and the inbox keeps ids for 30 days, so
an id is forgotten only after Kafka can no longer deliver its event. A service whose inbox
retention is not longer than its topic retention refuses to start. The mistake surfaces at the
moment of the change, in front of the person who made it, instead of weeks later as duplicates.
Expired ids are deleted hourly, in batches.

== How it is proven

* `MessagingPropertiesTest`
* `InboxIT` (expiry)
* `MessagingTopicsTest`

Starting order-service with `ecommerce.messaging.inbox.retention=7d` stopped it before it opened its
port or consumed a single event: "inbox.retention (PT168H) must be longer than topics.retention
(PT168H): events Kafka can still redeliver would be processed again".
